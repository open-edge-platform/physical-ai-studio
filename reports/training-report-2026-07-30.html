1 · Why the training failed

The failure was not caused by the training configuration, the dataset, the checkpoint patch, or loss divergence. The kernel log shows a hardware/firmware fault on the Battlemage GPU at PCI 03:00.0 that began 7 hours before training reported an error.

Root cause

GuC firmware 70.45.2 is installed; the kernel explicitly recommends 70.49.4. At boot the driver logs:

xe 0000:03:00.0: [drm] GT0: Using GuC firmware from xe/bmg_guc_70.bin version 70.45.2
xe 0000:03:00.0: [drm] GuC firmware (70.49.4) is recommended, but only (70.45.2) was found
xe 0000:03:00.0: [drm] Consider updating your linux-firmware pkg

The GuC (Graphics microController) schedules all GPU work. When its command transport stalls, the host CPU blocks in an MMIO read inside an interrupt handler — which is exactly the memcpy_fromio hard lockup at 00:42. Under a sustained multi-hour compute load this degraded until the firmware stopped responding entirely.

Evidence this is firmware/driver and not thermal or OOM: zero thermal-throttle entries, zero OOM-killer entries, and 22 GB RAM free at failure. The fault signature is entirely in the GuC command-transport path.

The overfitting pattern

Run 4 (c5d4500a) has the best train loss of any run (0.023) and one of the worst val losses (0.1917) — a 8.3× gap. It is also the only run to exceed one full epoch (1.19). Every good model on this box trained well under one epoch. That is why 2000 steps was chosen over 3000, and the choice still looks correct.

6 · What survived, and what to do next

Recovered artifact

7c1f0a94 — "Pi0.5 Sorting 150eps step1000" · registered in the GUI, ready to test.

  • All 819 float tensors verified: 0 NaN, 0 Inf, mean magnitude 0.59
  • exports/torch/pi05.pt — 9,354,284,578 bytes (byte-identical size to the known-good 15842eae)
  • exports/openvino/ — pi05.xml + pi05.bin (5.9 GB), tokenizer included
  • Promoted from cache/8108c5ba…/stepstep=001000.ckpt, DB row inserted manually (canceled/failed jobs never get one)

The checkpoint patch applied the night before is the sole reason this run produced anything. Under the previous configuration, monitor="val/loss" only fired on epoch boundaries — and one epoch is ~11,285 steps — so nothing would have been saved before the GPU died.

Fix the GPU before the next long run

  1. Update GuC firmware to 70.49.4. This is the direct fix for the confirmed root cause: 
    sudo apt update && sudo apt install --only-upgrade linux-firmware
# then verify after reboot:
sudo dmesg | grep -i "GuC firmware"
    If the packaged version is still 70.45.2, pull bmg_guc_70.bin from git.kernel.org/pub/scm/linux/kernel/git/firmware/linux-firmware.git into /lib/firmware/xe/.
  2. Watch for lockups during the next run — they were invisible from inside the training job: 
    journalctl -kf | grep -E "LOCKUP|GuC|G2H|reset started"
    Any hit means the GPU is degrading and the run will not finish.
  3. Keep the checkpoint patch. It is the only reason Run 10 wasn't a total loss. Consider dropping the interval to 500 steps for finer-grained insurance.
  4. Consider capping runs at ~1000–1500 steps until firmware is updated. The first lockup came at 1h32m; the card survived ~8.5 h before total loss. Shorter runs finish inside that envelope.

On the model itself

Val loss 0.1540 for 150 episodes is worse than 0.1187 for 91 episodes — but the two numbers come from different held-out splits, so this is suggestive, not conclusive. More importantly, val loss barely captures what the 59 new episodes were recorded to fix: full-travel-to-bin-center releases and single-block scenes. The arm is the real test. Run the same ~10 scenarios on 7c1f0a94 and 15842eae, restarting the container between models (each unload leaks ~9.1 GB VRAM).
