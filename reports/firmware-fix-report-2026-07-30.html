1 · What was wrong, and what fixed it

The prior report established that Run 10 died of a firmware fault, not a training fault. Two distinct symptoms shared that one root cause, and one firmware update plus a reboot cleared both.

ProblemSymptom beforeMechanismStatus now
A — Training death UR_RESULT_ERROR_DEVICE_LOST (20) GuC 70.45.2 stops acknowledging host commands; interrupt handler wedges the CPU; ~340 driver resets end in a dead device. FIXED
B — Models would not load UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY (39) The reset storm corrupted the driver's memory allocator. Raw big allocations still worked; many-small-tensor migration failed. Not fixable by docker restart — damage was in the kernel driver, so it needed the reboot. FIXED

The fix, in one line

Replace Ubuntu's /lib/firmware/xe with the linux-firmware tree from Intel's repo — GuC 70.45.2 → 70.65.0 — rebuild initramfs, reboot. The reboot also rebuilt the corrupted allocator state, which is why one action resolved both problems.

Zero faults at idle is necessary but not sufficient — Run 10's first lockup came 1 h 32 m into load. The firmware version check is conclusive; the stability claim is not proven until a long run completes. Monitor during the next run (§6).

7 · If it happens again

  1. Roll back the firmware if the new version misbehaves in a new way: 
    sudo rm -rf /lib/firmware/xe
sudo mv /lib/firmware/xe.backup /lib/firmware/xe
sudo update-initramfs -u && sudo reboot
  2. If lockups return on 70.65.0, firmware age is no longer the explanation. That would point at the kernel xe driver or the sustained-load thermal/power envelope, and it becomes a report worth sending to Intel with the journal attached.
  3. Error 39 after any reset storm means the allocator is corrupted again — reboot, don't bother with docker restart, and re-run the §5 staged test before trusting the card.

Two conclusions follow directly:

  • The first fault in the machine's entire history is Jul 30 00:41:42, mid-way through boot −2 — still on 70.45.2. Something changed on Jul 29, not on Jul 30 when the firmware was swapped.

The signature moved — and it points away from compute

Run 10's lockups had RIP: memcpy_fromio. Run 11's are all RIP: g2h_read. More decisive: every one of the 2,524 driver errors is on GT1, and GT1 is not the compute tile.

$ ls /sys/class/drm/card0/device/tile0/gt*/engines/
gt0/engines/:  bcs  ccs  rcs      # compute + render + copy — training runs here
gt1/engines/:  vcs  vecs          # video decode + video enhance — ALL 2524 errors here

$ grep -c "GT0" gpu-fault-watch-490a12e3.log      # 0 on the training tile
$ grep -oE "action [0-9]+" gpu-fault-watch-490a12e3.log | sort -u
action 3003                       # GuC power-state query — 100% of failures

Every failure is the same single operation: action 3003, a GuC power-state query against the media tile, timing out. The training workload on GT0 never faulted. That is why the job kept reporting healthy steps — the compute path genuinely was healthy, while the kernel's interrupt handler burned CPU cores spinning on a media-tile GuC that had stopped answering.

Why this kills the run anyway. The lockups are in xe_guc_irq_handler → xe_guc_ct_fast_path → g2h_read, an interrupt path. 398 hard lockups plus 1,435 soft lockups starved containerd, dockerd and rcu_exp_gp_kthr of CPU (visible in the log by name). Training froze at step 1473 at 05:16 and the job was only declared dead at 17:45 when the backend shut down — the GPU was fine, the host was wedged.

Both pre-Jul-29 runs completed all their training steps — 2000/2000 and 5000/5000 — and neither produced a model. 9200784f hung at the 24.5 GB final save on Jul 26 19:26 and was OOM-killed 19 hours later; ec4c4cef died during OpenVINO export. So training has already reached 5000 steps on this box; what failed was writing the result.

Consequence for step counts. The apparent “1000-step ceiling” is an artefact. ModelCheckpoint(every_n_train_steps=…, save_top_k=-1) writes interval checkpoints while training continues — Run 11's step-1000 checkpoint landed at 02:38 and training ran on to 1473. Every surviving model is a 1000-step model only because 1000 was the first interval and every run died before the second. Set a high max_steps, take interval checkpoints, and stop manually before the final save — that avoids Failure A entirely. The interval is now 5000 (local.py), since 12 × 22.8 GB would need 274 GB of disk.

Also note ec4c4cef trained on a 31-episode snapshot (17,536 frames), not 150 — which is why Lightning logged epoch=1 at 2000 steps. It is not comparable to the recent runs.

The candidate table above rates Prometheus polling an “AMPLIFIER.” A direct check weakens even that. This addendum initially argued against rolling back because 81 lockups is still broken. That framing was wrong. 81 lockups let Run 10 reach step 1750; 398 lockups killed Run 11 at 1473. The old firmware was measurably less bad, and the upgrade cut time-to-first-fault from 1 h 32 m to 9 minutes.

Ranked by evidence, the order to try is now:

  1. Kernel 6.17.0-40 — still installed in /boot. The only configuration with a genuinely fault-free week, and the boot table implicates the -40 → -41 change.
  2. Firmware rollback to 70.45.2 — blobs preserved at /lib/firmware/xe.backup/. Less bad, not fixed.

Still unexplained: what wakes GT1 at all. lerobot decodes video on the CPU via torchcodec, so the media tile should be idle during training. That gap is why the empirical tests above outrank further log analysis.

New leading candidate — deep CPU C-states race the GPU interrupt

Not considered in §9. The wedge is unchanged — a core stuck in the GuC message-ring read inside the interrupt handler, interrupts disabled, unable to yield — but the trace shows what the core was doing when the interrupt arrived:

RIP: 0010:g2h_read+0xb1/0x420 [xe]
 <IRQ>  xe_guc_ct_fast_path ← xe_guc_irq_handler ← gt_irq_handler ← dg1_irq_handler
 </IRQ>
 <TASK>
 RIP: 0010:cpuidle_enter_state+0xca/0x6e0     <- CPU4 was ASLEEP
 cpuidle_enter → call_cpuidle
 Comm: swapper/4                               <- the idle task

All 721 lockups are on CPU 4 only — the single core servicing that GPU IRQ. The idle configuration leaves a wide race window:

C3_ACPI   latency=1048us   usage=9,139,916    <- 1 ms exit latency, heavily used
intel_idle.max_cstate = 9                     <- unclamped
pcie_aspm.policy = default                    <- not "performance"

This is circumstantial, not proven. One-core concentration plus cpuidle_enter_state in the trace plus a 1 ms wake latency inside an MMIO read is a plausible race, but the deeper defect is that the driver has no timeout on that mailbox read. Clamping C-states may only make the wedge rarer, not absent.

Fixes — ranked, none applied yet

All require sudo from a real terminal. Item 1 needs a reboot and was deliberately not run unattended.

  1. Clamp C-states + ASPM — new, highest value, needs reboot. Costs idle power and heat; fully reversible. 
    sudo sed -i 's/GRUB_CMDLINE_LINUX_DEFAULT="quiet splash/GRUB_CMDLINE_LINUX_DEFAULT="quiet splash intel_idle.max_cstate=1 processor.max_cstate=1 pcie_aspm.policy=performance/' /etc/default/grub
sudo update-grub && sudo reboot
  2. Pin GPU IRQs off CPU 0/4 — no reboot, damage limitation only. Will not stop the wedge, but keeps a stuck core from starving rcu/dockerd — the same starvation §9 recorded, and what made the box unusable for 42 h. 
    echo 2 | sudo tee /proc/irq/179/smp_affinity_list   # B70 -> CPU2
echo 3 | sudo tee /proc/irq/184/smp_affinity_list   # B50 -> CPU3
  3. Shorten the engine job timeout — free, low expected value. job_timeout_ms is already 5000 (max 10000) at /sys/class/drm/card1/device/tile0/gt0/engines/rcs/ and it did not save this run: the wedge is in the IRQ handler, which never yields to let a timeout fire.
  4. Checkpoint every 250 steps + a progress watchdog — not a fix, but the only thing that makes a long run survivable. val_check_interval=1000 (local.py:106) meant a wedge at 1750 cost 750 steps; at 250 it costs ≤250. Add a watchdog that kills the job when no Training progress line has appeared for ~10 min — Run 12 hung silently for 42 hours. Remember the baked-source gotcha: docker cp to both container paths.

There is no true resume. base_model loads weights only (local.py:58-59) — no optimizer or LR-scheduler state. Restarting from a rescued checkpoint is not equivalent to continuing a run, so plan long runs around checkpoint frequency rather than around resuming.

§9's advice to cap runs at 1000 steps stands and is reinforced: Run 12 attempted 5000 and reached 1750. Every model that has actually worked on this box was trained at 1000.
