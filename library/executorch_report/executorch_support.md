    --extra-index-url https://download.pytorch.org/whl/nightly/cpu

# 3. CPU torch 2.14 - the nightly ExecuTorch pybindings are built against it (older torch fails in

uv pip install torch==2.14.1 torchvision==0.29.2 --index-url https://download.pytorch.org/whl/cpu

# 4. Nightly OpenVINO + tokenizers (same build). unsafe-best-match lets numpy etc. come from PyPI.

Transformers notes:

- Do **not** install LeRobot policy extras (`lerobot[pi]`, `lerobot[transformers-dep]`, ...): they
  pin `transformers<5.6`, which breaks the physicalai VLAs (Qwen3-VL, PaliGemma code paths). LeRobot
  0.6.0 policies run on 5.15.1 except pi0, which needs the `cache_position` shim (see below);
  lerobot 0.7.0 needs transformers 5.22.x, which the library does not support yet.
- Expect resolver warnings for lerobot (`torch<2.12`, `torchvision<0.27`, `torchcodec`); they are
  harmless for the matrix (no video decoding).
- Use CPU torch only: torch XPU builds and ExecuTorch do not work together. The `xpu` column uses
  the OpenVINO `GPU` plugin, not torch XPU.

## Where to fix: library vs ExecuTorch

The ExecuTorch flow is `torch.export.export` → `to_edge_transform_and_lower` (Core-ATen
verification + OpenVINO partitioning) → `.pte` → runtime. ExecuTorch only consumes the
`ExportedProgram`, so anything that fails *inside* `torch.export` (data-dependent Python control
flow, `.item()`/`.tolist()`, boolean-mask shapes) cannot be fixed in ExecuTorch — the model code
must change (upstream or a library shim). Failures after `torch.export` are ExecuTorch / OpenVINO
backend territory and are fixed there by preference.

| Problem | Fails in | Fix in | Why not ExecuTorch / why ExecuTorch |
|---|---|---|---|
| smolvla `aten.bucketize` (both sources) | `to_edge` verifier | **ExecuTorch + OpenVINO** (library fallback) | Post-export op coverage. OpenVINO has a native `Bucketize` op and the TorchScript frontend already maps `aten::bucketize`; the FX table (`openvino/frontend/pytorch/torchdynamo/op_support.py`) and the ET partitioner just don't list `aten.bucketize.Tensor`. |
| molmoact2, rldx1 OOM | unknown stage (SIGKILL) | **ExecuTorch** first, after measuring | If peak RSS is in lowering / OpenVINO compile / `.pte` serialization, it is ET memory use (model copies). If it is in `torch.export`, PyTorch. Library fallback: bf16. |
| xvla `aten.index_put` (`x[..., idx] = 0.0`) | OpenVINO PyTorch frontend (`AtenIndexPutReplacer`) | **OpenVINO** (library fallback) | Valid static graph; the FX translator fails on `None` (ellipsis) indices + scalar value. |
| diffusion DDPM | `torch.export` | Upstream diffusers / LeRobot; library shim meanwhile | `nonzero()[0][0]` + `if index == ...` in the scheduler; never reaches ET. |
| groot | library wrapper, then `torch.export` | Library | Wrapper design (no `NormalizerProcessorStep`) and Qwen3-VL `tolist()` geometry; XR0 patches already live in the library. |
| pi0_fast | eager, inside `predict_action_chunk` | Library | Model code decodes action tokens via text (`.tolist()`, tokenizer) and scipy `idct`; cannot be in any graph. |

## Changes already made

- **LeRobot language-token inputs** (`policies/lerobot/policy.py`). `_ActionChunkExportModule`
  bakes only the normalizer / unnormalizer into the graph; every other processor step runs on the
  host. Previously the export sample had no language tokens → `KeyError:
  'observation.language.tokens'` for every VLA. The wrapper now exposes
  `observation.language.tokens` and `observation.language.attention_mask` (INT64,
  `(tokenizer.max_length,)`) in `inputs_schema`; tokenization stays on the host (prompts need the
  trailing `"\n"` LeRobot appends for pi0 and smolvla). For xvla it also applies ImageNet
  normalization and adds `domain_id` in-graph. Eager check vs the full LeRobot pipeline: max
  |diff| 0.0 for pi0, smolvla, xvla.
- **LeRobot pi0 `cache_position` shim** (`policies/lerobot/policy.py`). lerobot 0.6.0
  `pi_gemma.py` passes `cache_position=` to `create_causal_mask`, which transformers 5.15.x no
  longer accepts (lerobot 0.7.0 drops it but needs transformers 5.22.x).
  `_patch_pi_gemma_create_causal_mask` drops the kwarg; remove it once lerobot >= 0.7.0. Verified:
  pi0 exports and runs (552 s).
- **LeRobot xvla static `forward_vlm`** (`policies/lerobot/policy.py`). Fixed
  `GuardOnDataDependentSymNode ... u0` (`modeling_xvla.py:177`). Stock `forward_vlm` reads the
  values of `image_mask` (built from `torch.ones` / `new_zeros` per camera in `_prepare_images`):
  `int(mask.sum().item())` and `if num_valid == 0` need a concrete value of an unbacked SymInt, and
  boolean-mask indexing (`flat_images[mask]`, `image_features[mask] = ...`) gives data-dependent
  shapes. `_xvla_static_forward_vlm`, bound with `types.MethodType` in `_export_module` (lerobot
  0.6.0), encodes every view and zeroes padded ones:

  ```python
  feats = self.vlm._encode_image(pixel_values.flatten(0, 1))      # static batch
  feats *= image_mask.reshape(-1, 1, 1).to(feats.dtype)            # zero padded views
  ```

  Eager |diff| 0.0 vs stock (3 views, 1 padded); the `num_valid == 0` check is dropped. Verified:
  the matrix now gets past `torch.export` (Florence2 DaViT converts). Upstream candidate for LeRobot.
- **physicalai xr0 `to_executorch`** (`policies/xr0/policy.py`). The generic path skipped
  `_bake_ingraph_export()` (vision geometry, RMSNorm, `tokenized_prompt` → `input_ids` aliasing),
  so the model got no `input_ids`. The override bakes, then calls the base export, like
  `to_openvino`. Eager after the bake: `(1, 30, 32)`, finite. Verified: exports and runs (461 s).
- **physicalai rldx1 `to_executorch`** (`policies/rldx1/export.py`). The generic path skipped the
  graph-safe model swap and the trimmed fp32 sample → `IndexError: mask [1152] vs tensor [1088]`, and
  `extra_export_args` failed on `backbone.qwen_config` (only the graph-safe backbone has it;
  `nn.Module.__getattr__` reported it as `extra_export_args` missing). The override mirrors
  `to_openvino`: fp32 weights, graph-safe swap, sample trimmed to `pixel_values`, `input_ids`,
  `position_ids`, `attention_mask`, `state`. Eager: `(1, 16, 7)`, finite. Matrix: both errors are
  gone; the export is now killed by the OOM killer after 283 s (see Open issues).
- **Matrix script** (`scripts/executorch_support_matrix.py`). The run step feeds the `.pte` the
  inputs listed in the exported `manifest.json` (`input_names`), cast to fp32, instead of the full
  sample (needed for rldx1). The eager reference is still computed before policy export prep, so
  `diff_cpu` stays `—` for xr0 / rldx1.
- **LeRobot pi05 / pi0_fast host-normalized state** (`policies/lerobot/policy.py`). Fixed
  `KeyError: 'observation.language.tokens'`. `Pi05PrepareStateTokenizerProcessorStep` /
  `Pi0FastPrepareStateAndLanguageTokenizerProcessorStep` discretize the *normalized* state into the
  prompt (`"Task: ..., State: 12 200 ...;\nAction: "`), so tokens depend on normalization, which
  was in-graph. For these policies (`_STATE_IN_PROMPT_POLICIES`) the host now runs normalize →
  prompt → tokenize (the LeRobot preprocessor up to `TokenizerProcessorStep`); the graph takes the
  normalized `observation.state` plus token ids / mask, and
  `_ActionChunkExportModule(host_normalized_state=True)` skips state normalization (images are
  still normalized in-graph). Eager check vs the full LeRobot pipeline: pi05 max |diff| 0.0.
  Matrix re-run pending. pi0_fast gets past the tokens but fails next (see Open issues).

## Open issues

Each section: **Error** (from the CSV), **Cause**, **Fix** (planned, not implemented).

### LeRobot pi0_fast — `AssertionError: Token sequence does not start with ['Action', ':']`

**Error.** Eager, after the language-token fix (random weights generate garbage tokens).

**Cause.** `PI0FastPolicy.predict_action_chunk` (`modeling_pi0_fast.py:1282`) samples action
tokens autoregressively (`sample_actions_fast[_kv_cache]`, up to `max_decoding_steps`, early
stop on EOS), then `detokenize_actions` (`:1176`) converts ids to text tokens
(`convert_ids_to_tokens(seq.tolist())`), asserts they start with `Action:`, BPE-decodes them
(`decode_actions_with_fast`, `:1120`) and applies scipy `idct`. The text / scipy half cannot be in
any graph; with trained weights the assertion passes, but `torch.export` would still fail on
`.tolist()` and string ops.

**Fix (library).** Split the graph at the action tokens: export the prefix + fixed-length
autoregressive decoding (`max_decoding_steps`, no early stop, greedy / fixed temperature) and output
action token ids; run `detokenize_actions` + FAST decode + `idct` + unnormalize on the host. Needs a
host postprocessor for the FAST tokenizer. Otherwise mark pi0_fast not exportable via the wrapper.

### LeRobot xvla — `OpConversionFailure: aten.index_put.default`

**Error.** `export_cpu` after the `forward_vlm` fix (232 s): OpenVINO frontend fails on
`aten_index_put_default_1` with input `f32[1,32,20]`, indices `SequenceMark` (list with `None`),
scalar value `f32[]`: `AtenIndexPutReplacer` callback throws (`Transpose` of the scalar value with a
rank-3 order) → `No conversion rule found for operations: aten.index_put.default`, plus
`torch::None` / `SequenceMark` unconverted.

**Cause.** `torch.export` now succeeds; the failure is in OpenVINO conversion during lowering.
`[1,32,20]` is the noisy action chunk in `JointActionSpace.preprocess` (`action_hub.py:162-165`),
called from `XVLAModel.generate_actions` (`modeling_xvla.py:267`) every denoising step:

```python
proprio_m[..., self.gripper_idx] = 0.0   # index_put_default
action_m[..., self.gripper_idx] = 0.0    # index_put_default_1  <- fails
```

`...` exports as `None` entries in the index list; `AtenIndexPutReplacer` does not handle leading
`None` indices with a scalar (broadcast) value. `postprocess` (`action_hub.py:171`,
`action[..., gripper_idx] = sigmoid(...)`) has the same pattern with a tensor value and is the
next likely failure.

**Fix (preferred, OpenVINO).** `AtenIndexPutReplacer`: support `None` indices (expand to full
ranges / move indexed dims) and broadcast scalar values before the transpose.

**Fallback (library).** Patch the action space on the export instance with static masks:

```python
keep = torch.ones(dim); keep[list(gripper_idx)] = 0          # built once, eager
proprio_m, action_m = proprio * keep, action * keep           # preprocess
action = torch.where(keep.bool(), action, action.sigmoid())   # postprocess
```

Same values as stock, no `index_put`.

### LeRobot groot — `StopIteration`

**Cause.** `LeRobotPolicy._export_module` does
`next(s for s in preprocessor.steps if isinstance(s, NormalizerProcessorStep))`. Groot has no such
step: `GrootN17PackInputsStep` normalizes and pads internally, `GrootN17VLMEncodeStep` runs the
Qwen3-VL processor (chat template, image transforms, tokenizer) on the host, and the Qwen3-VL
backbone itself is data-dependent (`image_grid_thw.tolist()` in MRoPE and the vision tower).

**Fix.** Dedicated `_GrootExportModule` (inputs: packed/normalized `state`, `input_ids`,
`attention_mask`, `pixel_values`; baked `embodiment_id` and `image_grid_thw`; no bf16 autocast, no
RTC) running `GR00TN17.get_action`. The Qwen3-VL backbone needs the same export patches XR0
already has (`xr0/qwen3_vlm.py`, `xr0/export_openvino.py`) — move them to a shared module, compute
text position ids in-graph from `attention_mask`. Pack / VLM-encode / action-decode steps stay on
the host (not expressible as Runtime processors yet).

### LeRobot diffusion — `GuardOnDataDependentSymNode` (declares ET support)

**Cause.** `torch.export` fails in diffusers 0.42.1 `DDPMScheduler.previous_timestep`:

```python
index = (self.timesteps == timestep).nonzero(as_tuple=True)[0][0]
if index == self.timesteps.shape[0] - 1:  # data-dependent guard
```

No existing test exports LeRobot diffusion to ExecuTorch.

**Fix.** Not fixable in ExecuTorch (fails inside `torch.export`). Either the declared support is
wrong for DDPM or it only holds for another scheduler (DDIM — not verified). Check DDIM; otherwise
upstream a static `previous_timestep` (timesteps are fixed per call) or drop the ExecuTorch claim
for DDPM.

### smolvla (physicalai and LeRobot) — `aten.bucketize.Tensor is not in Core ATen opset`

**Cause.** Edge-dialect verification rejects `aten.bucketize`. Source: transformers
`SmolVLMVisionEmbeddings.forward` (`modeling_smolvlm.py:123-124`) buckets patch coordinates to build
position ids. physicalai smolvla reaches it via `vision_model.embeddings(...)`
(`policies/smolvla/model.py:1631`), LeRobot smolvla via `vision_model(...)`.

An `EdgeCompileConfig(_core_aten_ops_exception_list=[torch.ops.aten.bucketize.Tensor])` alone only
silences the check: the OpenVINO FX op table does not list `aten.bucketize.Tensor` (only the
TorchScript `aten::bucketize`), so the partitioner leaves it on the portable runtime, which has no
kernel for it.

**Fix (preferred, ExecuTorch + OpenVINO, no library change).**

1. OpenVINO PyTorch frontend: register `aten.bucketize.Tensor` in the FX op table and
   `torchdynamo/op_support.py`, reusing the existing `aten::bucketize` → `Bucketize` translator.
2. ExecuTorch OpenVINO backend (`backends/openvino/partitioner.py`): add
   `torch.ops.aten.bucketize.Tensor` to `ops_to_not_decompose`, so `to_edge_transform_and_lower`
   preserves it for the delegate instead of failing Core-ATen verification.

ET-only alternative if OpenVINO cannot change: a bucketize → compare + `sum` decomposition pass in
the ExecuTorch OpenVINO backend (benefits every model, not only ours).

**Fallback (library, until the above ships).** Decompose it in `_export_executorch_pte`:

```python
def _bucketize_decomp(x, boundaries, *, out_int32=False, right=False):
    cmp = x.unsqueeze(-1) >= boundaries if right else x.unsqueeze(-1) > boundaries
    return cmp.sum(-1, dtype=torch.int32 if out_int32 else torch.int64)

table = torch.export.default_decompositions()
table[torch.ops.aten.bucketize.Tensor] = _bucketize_decomp
aten_dialect = aten_dialect.run_decompositions(table)
```

Exact for 1-D sorted boundaries. Next possible blocker: the boolean `index_put`
`position_ids[mask] = pos_ids[mask]` in the same function (all-true mask for smolvla, so it can be
replaced by `arange` if the partitioner rejects it).

### physicalai molmoact2, rldx1 — `OOM? (SIGKILL)`

**Error.** molmoact2: SIGKILL after 823 s; rldx1 (after the `to_executorch` fix): SIGKILL after
283 s. No Python traceback; rldx1's log ends right after model / tokenizer loading, so the stage is
unknown.

**Cause.** Almost certainly the kernel OOM killer. Weights alone are ~22 GB (molmoact2, 5.4B) and
~28 GB (rldx1, 6.9B) in fp32 (rldx1 is cast to fp32 for export by `fp32_weights_for_export`);
ExecuTorch lowering holds several copies of the model (exported program, edge program, delegate
blob, serialized `.pte`), which can exceed 93 GB RAM. xr0 (4.7B) fits (461 s).

**Fix.** First measure peak RSS per stage (`torch.export`, `to_edge_transform_and_lower` /
OpenVINO compile, `to_executorch` + serialization). If the peak is in the ExecuTorch stages (likely:
edge program, delegate blob and `.pte` buffer each hold the weights), fix it in ExecuTorch /
the OpenVINO backend: free the edge program after lowering, stream serialization, or keep delegate
weights external instead of duplicating them in the blob. Library fallback: add swap (keeps fp32
results) or export in bf16 (halves memory, but tests bf16 support).
The script now reports this case as `OOM? (SIGKILL)`.
